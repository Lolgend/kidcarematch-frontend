# Frontend behavior and backend contract boundaries

Research snapshot: 2026-11-06. Read-only source review of the frontend and its sibling backend. No application or backend code was executed, and no production requests or credentials were used. Paths and line numbers refer to the checked-out source snapshot.

## Scope and confidence

The active-looking app is the repository-root Vite app (`package.json`, `index.html`, `src/main.jsx`). A second Vite/React scaffold exists under `kidcare-match/` with its own `package.json`, entrypoint and assets; it appears scaffold-like from filenames, but active deployment/build ownership needs confirmation from project configuration and maintainers. Root scripts expose dev/build/preview/start; no test script or test dependency appears in root `package.json` (lines 6–21). `dist/` and `node_modules/` were excluded from inspection as generated/dependency artifacts.

The frontend has one large orchestration file (`src/main.jsx`) importing Firebase, shared API helpers and the admin dashboard (lines 1–46). This makes journeys and state transitions discoverable in source but does not establish what is reachable or correct in a running deployment. Findings below are candidate coverage boundaries, not a completed behavioral audit.

## Contract mismatches and uncertainty to prioritize

1. **Notifications API absent in the inspected backend route inventory.** Frontend calls `/api/v1/notifications`, `/read`, and `/read-all` (`src/api.js`, lines 192–209). Its comment explicitly describes a fallback when the notifications endpoint is absent or fails (`src/main.jsx`, lines 369–370). Verify whether deployment uses another router/version; otherwise treat the fallback as intentional degraded behavior, not a contract implementation.
2. **User reviews API helpers have no matching router in the backend file inventory.** Frontend exposes `/api/v1/reviews/me` and review PATCH/DELETE (`src/api.js`, lines 233–250), while the discovered backend router files include centres, reviews, users, watchlist, profile, and admin. The backend `reviews.py` may or may not define equivalent paths; route-level comparison is required before claiming a mismatch.
3. **Configuration names differ.** Shared requests use `VITE_API_URL` (`src/api.js`, lines 4–13), whereas admin requests use `VITE_API_BASE_URL` (`src/admin/adminApi.js`, lines 3–10). Confirm deployment defines both consistently; this can produce user features working while admin reports unconfigured (or vice versa).
4. **Firebase and Firestore.** `src/firebase.js` initializes both Auth and Firestore (lines 1–18), but the active main file imports only `auth`; no Firestore calls were found in the scanned app/admin files. Firebase project identifiers are present in client config; this is not a server secret, but no credentials or environment files were inspected.
5. **Root vs nested scaffold ambiguity.** Root and `kidcare-match/` both contain Vite app structures. `firebase.json` and both package/config sets must be compared before declaring which is deployed. The nested app may be stale scaffold or a separate artifact; source presence alone cannot decide.

## Backend contract evidence to use (not intended frontend truth)

- Backend route declarations and schemas are implementation evidence; schema defaults, response wrappers, and error status codes should be captured directly from route/schema code during a follow-up contract comparison.
- Backend tests under `backend/tests/` provide additional examples of implemented behavior, including API auth, centre, profile, review and watchlist flows. They were not executed per issue instructions.
- Backend ADRs describe intended architecture; where they differ from current route/schema behavior, record both and ask maintainers which is authoritative. No frontend ADR/glossary was found in the frontend root or its `docs/adr` directory at this snapshot. Backend vocabulary includes Preschool Centre, Vacancy Record, Family Preference Profile, Review, Watchlist Entry, User, Firebase UID, and Administrator (`backend/GLOSSARY.md`).

## Candidate journey/risk inventory for a later unchanged-behavior baseline

1. Anonymous browse: initial data load, filters/districts, centre detail, public reviews, API unavailable/empty/error states.
2. Parent account lifecycle: email and Google auth, profile bootstrap, reload/refresh, sign-out and account switching.
3. Family Preference Profile: incomplete onboarding, save/edit, reload, local/server reconciliation, month and weight conversions, match ranking/explanations.
4. Watchlist/alerts: add/remove, legacy local data migration, backend failure fallback, per-user storage isolation, notification read states.
5. Reviews: submit/edit/report, duplicate prevention, limits and moderation transitions.
6. Administrator: authorization denied/allowed, search/filter/pagination, all destructive or mutating operations, confirmation cancellation, server errors, reauthentication-sensitive account edits.
7. Cross-cutting: all API token/no-token cases, 401/403/404/422/5xx handling, network outage, malformed/partial responses, browser storage disabled/corrupt, clock and timezone dependence, responsive layouts, keyboard/screen-reader states.

This inventory is provisional. Tests should assert user-visible behavior and documented contracts; where `main.jsx` owns business logic internally, coverage should not depend on private helper implementation details. First obtain a human-confirmed expected behavior for suspected defects and mismatches before preserving them as a baseline.

## Limits

Static review cannot establish deployed environment values, runtime reachability, data freshness, actual Firebase project settings, browser-specific behavior, accessibility conformance, or performance. It also cannot determine whether a suspicious behavior is a regression or an intended product rule. A later baseline needs controlled local fixtures and network/auth boundaries, followed by limited manual checks against agreed non-production configuration; production data/credentials are unnecessary for this source inventory.
