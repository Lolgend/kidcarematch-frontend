## Static comparison and matching behavior

`compareSelectedIds` is React component state initialized to an empty array (`src/main.jsx:526-530`); `compareDetails` is another component state map (`src/main.jsx:553`). The comparison page is an in-app page selected through `setPage` (`src/main.jsx:907-927`). Selection is therefore retained while that component remains mounted and the user changes app pages, but neither selection nor details are written to browser storage. Reload persistence is not established by a runtime check; the source state initialization indicates selection starts empty after a fresh mount.

Comparison candidates come only from the local saved-centre list (`src/main.jsx:1412-1424`). The comparison page accepts checkbox selections up to three, offers clear and per-card removal actions, and renders a side-by-side view (`src/main.jsx:2074-2169`, `2244-2253`). Removing a Preschool Centre from the saved list also removes it from comparison (`src/main.jsx:1057-1082`). The selected list is mapped through the centre lookup and capped at three (`src/main.jsx:1420-1424`). Detail is requested once per selected centre from the centre-code route when a code exists, otherwise by numeric ID; a fulfilled or failed request is stored by ID (`src/main.jsx:1426-1438`).

The comparison fields include centre contact, services/fees, transport, hours, and vacancies. Missing values use text such as “Not provided,” “Fee data unavailable,” or “None listed”; a failed detail request retains list data and shows an inline error (`src/main.jsx:2171-2238`). The grid uses `minmax(240px, 1fr)` per selected Preschool Centre and `overflowX: auto` (`src/main.jsx:2162-2169`). The selection form becomes one column at viewport widths up to 800px (`src/styles.css:16-21`); the actual narrow-screen usability and horizontal scrolling remain unverified.

The shared API exposes list, detail-by-ID and detail-by-code requests (`src/api.js:96-113`). At the backend revision, `/code/{centre_code}` and `/{centre_id}` return the detail response (`api/v1/centres.py:378-390`, `597-609`); the schema extends the list item with vacancy records, services and review summary (`schemas/centre.py:70-120`). This supports the request and displayed-field comparison at source level only. Request compatibility and rendered field behavior have not been exercised against an isolated service.

Frontend matching does not call the backend `/api/v1/centres/match` route. It fetches centre candidates through `getCentres`, then fetches details in batches of eight through `getCentreById`, caching each detail in an in-memory `Map` (`src/main.jsx:1234-1327`; cache initialization at `560`). It widens the requested postal sectors when candidate counts are small (`1270-1291`) and computes vacancy, cost, travel and total scores in the browser (`1185-1232`). The backend has a separate matching endpoint and ADR describing a three-factor weighted model, subsidy calculation, two-stage routing, and explanation service (`api/v1/centres.py:612-625`; backend ADR 0007). These are separate implementations; this report makes no equivalence or product-intent claim. The already-recorded profile/matching discrepancy in `docs/audit/family-profiles.md` remains the cross-engine finding; it is not duplicated here.

## Finding

### CMP-F-01 — Comparison selection does not survive a fresh app mount

- **Category / affected journey:** Comparison; selection and reload.
- **Classification:** Observed behavior.
- **Evidence:** Frontend revision `c8a627d740fcaf618cf28b6100bf29e94024fd13`; `src/main.jsx:526-530` initializes selection as empty component state, `src/main.jsx:553` keeps detail responses in component state, and `src/main.jsx:907-927` changes pages without navigation state or storage persistence. No comparison key is written to storage in the inspected comparison flow.
- **Reproduction / limitation:** Static inspection shows a fresh component mount initializes an empty selection. No browser reload was run, so rendered reload behavior is not independently observed.
- **Impact:** A user returning after a reload may need to choose the Preschool Centres again; whether this is undesirable is not established by the approved matrix or an available frontend ADR.
- **Severity:** Low — the source indicates a loss of convenience/session state, with no demonstrated loss of persisted Watchlist Entries or other data.
- **Confidence:** High for the component-state initialization and absence of persistence in the reviewed comparison flow; low for any claim about intended persistence.
- **Status:** Open, unresolved; product intent and remediation are not inferred.

## Reproducible performance procedure (future safe run)

No measurement is published because the required isolated runtime and measurement environment were not available for this documentation-only ticket. The procedure below specifies a repeatable safe run; it is not an instruction to use production. Stop and leave the scenario unverified if the API, Firebase project, maps/other external requests, and all write targets cannot be shown to be isolated and non-production. Do not launch the app as part of this ticket.

### Fixed synthetic fixture `KCM-PERF-01`

Use a local, isolated fixture service with deterministic responses and no external egress. Do not seed a real database or use production data. The fixture contract is:

- 240 Preschool Centre list items with synthetic IDs `900001`–`900240`, codes `PERF-001`–`PERF-240`, generated names such as `Synthetic Centre 001`, and no personal data.
- Each list item has the fields needed by the frontend mapping and matching path: centre ID/code, name, postal code, address, district, and a synthetic open-vacancy indicator. Use a documented deterministic postal-sector assignment: 12 items for sector `12`, 12 for sector `34`, then two items for each of the other 80 sectors `01`–`82` and one extra item for each of the first 56 remaining sectors in ascending order. This assigns the remaining 216 items exactly.
- Detail records for the 24 sector-12/sector-34 candidates include deterministic centre fields, `services`, `vacancies`, `transport_provided`, hours, and review summary. Provide matching `n1`/`SC` fee and an open vacancy for 20 records; provide a missing fee for 4 records to exercise the “not ranked” path. Assign stable integer fees `$500` through `$1,450` in `$50` increments, cycling from the first value. Give each record one vacancy month and status; use synthetic month `2027-01` and status `Available`.
- Directory/detail requests return byte-for-byte stable JSON and fixed success latency of 0ms in the local service. The browser should have no network or CPU throttling. If a different fixed latency is chosen to make traces legible, record the exact value and apply it to every run.
- Matching inputs are home postal code `123456`, workplace `345678`, level `n1`, citizenship `SC`, budget `$750`, and weights vacancy/cost/travel `50/35/15`. The two sectors return exactly 24 unique candidates, so the source count thresholds do not widen the search. All fixture IDs/codes and values are fabricated solely for this procedure.

### Run and record

1. Record frontend commit/build, OS/version, hardware/CPU and memory, exact browser/version, DevTools or other measurement tool/version, local fixture service/version, viewport, zoom, and any network/CPU throttling. Record whether browser extensions, service workers, or other background processes are present. Use a clean disposable profile and synthetic/non-production Firebase/API settings. Keep all API and write destinations on isolated local fixtures.
2. Use a cold run with a fresh browser context/profile, cleared site storage, disabled browser cache, and no prior matching/detail request. Capture five runs each for directory load, one fixed Preschool Centre detail, and matching. Do not count service start-up or tool start-up as app time; note fixture readiness separately.
3. Use a warm run in the same app session immediately after one completed cold run for each journey, without clearing browser or in-memory state. Capture five runs for each journey and record cache/storage state. In particular, matching's `matchDetailCache` is in-memory and should be warm on its repeat run; still record candidate-list requests separately. Do not pool cold and warm results.
4. Define and record a consistent start/end event per journey using browser trace timestamps: directory navigation start to populated directory results visible; centre-card activation to populated detail content visible; matching action to final ranked list and completion message visible. Capture network and main-thread traces so request wait is distinguishable from rendering. No source instrumentation, private-helper exposure, or new automation is authorized by this slice.
5. Record each raw run in milliseconds, then report median and p95 separately for cold and warm, plus request counts and skipped/missing detail count. Include sanitized trace artifact paths/links and a note describing any missing event or failed run. These are initial measurements, not a pass/fail threshold. Never substitute invented timings when a run is unavailable.
