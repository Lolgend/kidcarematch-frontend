# Family Preference Profile and matching audit

## Scope and evidence basis

This slice records the existing Family Preference Profile and matching behavior without changing application code. Frontend evidence is revision `58e1ec0de67030be7924587c4e76c016fc17519c`; backend source is read-only revision `db7fef7cc0e8691c83fc49623212ef35093c11d7`. Fixtures used by the wrapper tests are invented synthetic values and make no claim about a live account or service.

The approved automated seam is the existing shared API wrapper. `getFamilyProfiles`, `createFamilyProfile`, and `updateFamilyProfile` are tested through exported operations with Firebase mocked and an explicit fail-closed `fetch`. No matching wrapper exists in `src/api.js`; matching, profile conversion, storage, and UI state are assessed statically. There is no app launch, backend process, identity provider, browser, storage manipulation, clock control, or live request in this evidence.

Run the focused suite with `npm run test:unit -- tests/api/family-profiles.test.js`. Result: 1 file and 12 tests passed on Node `v24.14.0`, npm `11.9.0`, and Vitest `3.2.4`; the pass is wrapper behavior evidence only. The tests cover list/create/update route and method, JSON payload and response preservation, percent-encoded member ID, token/no-token, token/fetch rejection, HTTP 401/403/404/422/500/503, JSON/text/204 responses and JSON parse failure. The shared harness rejects unconfigured requests. UI orchestration, storage, conversion, and matching helpers are outside wrapper coverage; no whole-application coverage claim is made.

The focused coverage command (`npm run test:coverage -- tests/api/family-profiles.test.js`) also passed 1 file / 12 tests. Its collected shared `src/api.js` coverage was 68.92% statements, 69.23% branches, 15.38% functions, and 68.92% lines. The unimported `src/admin/adminApi.js` was 0% in this focused run. These are full-module figures from the focused suite, not family-profile-only or application coverage; aggregate coverage is handled in parent reconciliation.

## Static source findings

| ID | Classification and affected area | Evidence and observation | Impact, severity, confidence, status |
|---|---|---|---|
| FFP-01 | Contract mismatch; profile lifecycle | The frontend saves one fixed-name profile, requests the collection and consumes only its first item (`src/main.jsx:194-210`, `589-597`, `1351-1354`). The backend exposes a parent-owned multi-profile collection and profile-name uniqueness (`api/v1/profile.py:57-68`, `130-140`; `docs/adr/0006-family-preference-profile-lifecycle-and-schema.md:9-11`). | The current UI does not expose choosing among profiles that the backend can store. Severity: **moderate**, because profiles for distinct children/scenarios cannot be selected in this UI. Confidence: **high** for the source-level mismatch; no deployed behavior was checked. Status: unresolved finding; product intent/remediation not inferred. Linked scenarios: FP-03, FP-04, FP-08, FP-09. |
| FFP-02 | Contract mismatch / observed algorithm difference; profile weights and ranking | Local ranking uses vacancy/cost/travel weights and local fee/vacancy/location calculations (`src/main.jsx:1185-1232`). Saving derives a cost/travel split and omits `vacancy_weight`; loading reconstructs preset rank weights from the cost share and does not use the response's vacancy weight (`src/main.jsx:193-210`, `213-227`, `253-266`). Backend profile response/schema includes all three weights, and its matching algorithm uses the three weights with conditional normalization when cost/travel factors are unavailable (`schemas/profile.py:146-162`, `214-233`; `core/matching.py:655-684`). | A local rank can be converted to a two-factor split, but exact three-factor preferences are not represented by that split; backend matching has separate scoring/availability behavior. Cross-engine ranking equivalence is not established. Severity: **moderate**, because displayed ordering may differ if persisted preferences are reused by backend matching. Confidence: **high** that the implementations differ in source; deployed account results were not compared. Status: unresolved finding; intended authority and equivalence remain a user decision. Linked scenarios: FP-05, FP-06, FP-07, FP-10. |

These are source comparisons, not evidence that the frontend or backend algorithm is the intended product requirement. No matching API wrapper is present or added for testing.

## Reproduction

From a clean checkout with the committed lockfile and documented test tooling installed:

```text
npm run test:unit -- tests/api/family-profiles.test.js
```

The focused test file stubs both API base variables to `.invalid`, mocks Firebase before importing the shared API wrapper, and installs `failClosedFetch`. It makes no real network request and requires no credentials, storage, service, or browser. This slice leaves full-suite and coverage aggregation to the parent baseline reconciliation.
