## Supported wrapper behavior

`getMyWatchlist()` defaults to `limit=100`; custom values serialize through `URLSearchParams`, repeat array keys, and omit null/empty values. The backend route defaults to 20 when no limit is supplied, accepts 1–100, and supports offset pagination (`watchlist.py:98-109`); the frontend explicitly supplies 100 by default. `createWatchlist` posts the caller's JSON unchanged. `deleteWatchlist` percent-encodes the watchlist identifier as a single path segment and sends DELETE. `getNotifications()` defaults to `limit=20`; custom queries use the same shared encoding. `markNotificationRead` encodes the identifier and posts to its `/read` subpath; `markAllNotificationsRead` posts to `/read-all`. All six operations use the shared Firebase bearer-token behavior. The wrappers pass successful JSON through unchanged, return `null` for 204, and propagate HTTP, fetch, token, and JSON parse errors.

At backend revision `db7fef7cc0e8691c83fc49623212ef35093c11d7`, `/api/v1/watchlist` supports authenticated create, list `/me`, and delete routes (`api/v1/watchlist.py:24-42, 92-114, 180-189`). The create schema requires `centre_id`, `level`, and `enrollment_month_year` and normalizes the month to UTC day one (`schemas/watchlist.py:10-23`). The list response includes enriched current vacancy status and pagination (`api/v1/watchlist.py:126-177`; `schemas/watchlist.py:38-62`). The frontend sends the matching create fields (`src/main.jsx:1106-1114`). This is static compatibility evidence, not a live contract check.

Backend ADR `docs/adr/0005-admin-portal-and-operations-architecture.md`, decision 4, specifies that account suspension preserves relational Watchlist Entries while revoking authentication and API access. That server persistence decision does not establish browser-key account separation or local alert persistence. The mocked 401/403 wrapper cases verify only error propagation; they do not verify the ADR's server authorization behavior.

No notification route or notification schema exists under the pinned backend `api` or `schemas` trees. The three frontend notification wrappers therefore have no matching route in this snapshot. A mocked 404 verifies only frontend error propagation; the UI's local fallback is separate behavior and no server notification delivery or persisted read state is demonstrated.

## Findings

Classification values follow the approved plan: **observed behavior**, **contract mismatch**, **suspected bug**, or **confirmed requirement**. Severity and confidence are independent and each has its own rationale. Status is **unresolved**; this evidence slice makes no fix or product-intent decision.

### W-01 — Browser-wide legacy watchlist is merged into each signed-in account

- **Category / journey:** account separation and persistence; Watchlist Entry lifecycle (P1).
- **Classification:** suspected bug. The code behavior is directly observable, while whether shared-browser carryover is intended has not been confirmed.
- **Evidence:** `src/main.jsx:531-537` initializes from the unscoped `kidcare-watchlist` localStorage key. Authenticated account loading (`src/main.jsx:663-716`) merges all locally stored IDs with the current user's server entries and writes the merged set back to that same global key. There is no Firebase UID in this key or merge filter. The server route, in contrast, filters entries by `current_user.user_id` (`backend api/v1/watchlist.py:115-116,145`).
- **Reproduction / limitation:** Static trace: save an ID in browser storage while account A is active, switch to account B in the same browser, and let the auth listener load B's server watchlist. The legacy ID remains in `saved`, is merged into B's displayed set, and the reconciliation effect may create a server subscription for B (`src/main.jsx:777-804`). No UI/account-switch runtime was run.
- **Impact:** Centre selections can appear to belong to another User and be subscribed under the new User after account switching on a shared browser.
- **Severity:** Medium — potential cross-account disclosure of saved centre choices and unintended per-user subscription; no credentials or server authorization bypass is evidenced.
- **Confidence:** High for global-key merge behavior from source; Medium for user-visible impact because UI execution and intended legacy migration policy were not verified.
- **Status:** Unresolved; user intent and remediation are outside this baseline.

### W-02 — Notification wrappers target routes absent from the pinned backend

- **Category / journey:** API compatibility; vacancy alerts/read state (P1).
- **Classification:** contract mismatch in the inspected revisions; deployment routing may differ and is not established.
- **Evidence:** `src/api.js:196-208` targets GET `/api/v1/notifications`, POST `/{id}/read`, and POST `/read-all`. Backend revision `db7fef7cc0e8691c83fc49623212ef35093c11d7` has no notification route/schema in `src/kidcarematch_backend/api` or `schemas`; its app mounts the watchlist router. Frontend fallback is explicit at `src/main.jsx:368-371,734-751`.
- **Reproduction / limitation:** Static route inventory; automated tests mock 404 and confirm error propagation but do not launch or query a service.
- **Impact:** On the inspected backend contract, server-persisted notification list/read requests cannot be fulfilled by these routes. UI code falls back to alerts derived from current watchlist data.
- **Severity:** Low — the source has a local fallback for notification-load failure; external delivery and durable server read state are unavailable in this contract snapshot.
- **Confidence:** High for the pinned source snapshots; deployment/runtime availability is unverified.
- **Status:** Unresolved contract/deployment question.

### W-03 — Local vacancy alerts and their read state are browser-derived, not server notifications

- **Category / journey:** persistence and notification semantics (P1).
- **Classification:** observed behavior; not a requirement that local alerts equal server notifications.
- **Evidence:** `src/main.jsx:368-438` builds alerts from `getMyWatchlist()` entries with an open `current_vacancy_status`; keys read state by `kidcare-alerts:${uid}`; local IDs contain the watchlist ID and status; closed/reopened status alters local records. `src/main.jsx:1023-1045` writes local read state for `local:` IDs and server endpoints for other IDs. Storage errors are swallowed at `374-378,434-438`.
- **Reproduction / limitation:** Static source trace only. No vacancy change, browser storage, account switch, polling timer, browser notification, or external delivery was exercised.
- **Impact:** Local unread count and alert history depend on the current watchlist response and that browser's storage; they do not demonstrate delivered or durable server notifications.
- **Severity:** Low — limitation is documented in source and the UI provides a fallback, but users may otherwise interpret “alert” as server-persisted or externally delivered.
- **Confidence:** High for local generation and storage behavior; Low for actual delivery expectations because no product requirement or runtime evidence was supplied.
- **Status:** Unresolved semantics; preserve the distinction in reports.

## Boundaries and limitations

The automated suite exercises only the six exported request wrappers. It does not test React state, per-User localStorage, real authentication, actual notification routes, API authorization, external delivery, vacancy polling, reload, account switching, browser accessibility, or responsive layout. No app launch, browser audit, backend run, production probe, source change, application dependency change, or storage-based integration test was performed. All manual checks remain gaps rather than passes.
